# Design: Backend-Driven Shared Story Gallery (with per-page images)

_Date: 2026-07-19_
_Status: Approved design — ready for implementation planning_

## Summary

Move generated stories out of browser `localStorage` and into a **backend that is the
source of truth**. Every browser reads the same **shared global gallery**: whoever
generates a story, it appears in everyone's Stories grid. Add a **per-page illustration**
to each story so early readers (5–8) stay engaged. Keep the story format **flexible**
(stored as a JSON blob) because the schema is not finalized.

This is an MVP. Identity, per-user scoping, moderation, an admin dashboard, and age-based
filtering are explicitly **later phases**.

## Motivation

- **Primary goal:** stories generated by anyone should be viewable by everyone (a shared
  family/community gallery). `localStorage` is per-browser/per-device and cannot do this.
- Secondary: `localStorage` has a ~5MB cap (~25 stories) and loses data on browser clear.
- We accept that this **reverses several locked `CLAUDE.md` rules** (see Scope Changes).
  That is a deliberate, documented decision, not drift.

## Non-Goals (explicitly out of this MVP)

- Identity / accounts / auth / per-user scoping (planned next phase).
- Admin dashboard to upload/manage stories (planned).
- Age-based filtering behavior (the `age_tag` column exists; the filter does not).
- Offline caching of generated stories (online-only, on-demand). Story format may still
  change, so we avoid building cache logic that would need reworking.
- Delete / moderation of gallery stories (planned).
- Migrating existing `localStorage` stories (earlier stories are disposable).

## Architecture

```
Child taps "Make my story"
   │
   ▼
POST /api/generate-story ──► OpenAI: 1 text call, then 6 images IN PARALLEL
   │                          │
   │                          ▼
   │                     upload 6 JPEGs ──► Vercel Blob ──► 6 URLs
   │                          │
   ▼                          ▼
   └──────────────► INSERT row into Postgres (Neon)
                          │
                          ▼
                    returns { story }   (full story + image URLs)

Stories grid ──► GET /api/stories?language=en ──► [ {id,title,cover_url,age_tag,created_at} ]
Story viewer ──► GET /api/stories/:id          ──► full story JSON + per-page image URLs
```

Backend = source of truth. Browsers hold only session-memory cache + rate-limit count.

## Data Model

One Postgres table (Neon). Only the fields the **grid list** needs are promoted to real
columns for a fast, lightweight query; everything else stays in a flexible `jsonb` blob.

| column       | type          | purpose                                                        |
|--------------|---------------|----------------------------------------------------------------|
| `id`         | uuid (PK)     | story id                                                       |
| `created_at` | timestamptz   | ordering (newest first)                                       |
| `language`   | text          | cheap filter for en/te grid                                   |
| `title`      | text          | grid list without parsing JSONB                              |
| `cover_url`  | text          | grid thumbnail                                                |
| `age_tag`    | text          | e.g. `"5-8"`. Real column so a future age filter is indexed.  |
| `story`      | **jsonb**     | the entire `GeneratedStory` blob — **format free to change**  |

Index: `(language, created_at desc)` for the list query; `age_tag` reserved for future
filtering.

**Why JSONB:** the story shape is not finalized (per-page images, captions, age-driven
image/text ratios). A blob column means schema changes need **no migration**. Only the 4
list-facing fields are structural.

**Future age vision (not built now):** `age_tag` will drive the image-to-text ratio —
e.g. `2-4` → more images / shorter text; `7-8` → fewer images / richer text. The JSONB
blob supports these variations in the same table.

### Type changes (`src/lib/types.ts`)

```ts
// GeneratedStory evolves:
pages: Array<{ text: string; image_url: string }>   // was { text: string }; image_url "" if that page's image failed
cover_image_url: string                              // now a Vercel Blob URL (was "")
// REMOVED: cover_image_data_uri (no base64 stored anywhere anymore)
age_tag: string                                      // defaults "5-8"
```

## Backend Endpoints

### `POST /api/generate-story` (evolves)
- Validates `character_id` / `theme_id` / `language` against locked enums (unchanged).
- Enforces the **server-side global daily cap** (see Rate Limiting) before spending money.
- Generates text, then images (see Image Flow), uploads to Blob, **inserts the row**,
  returns `{ story }` with URLs.
- `child_name` used only to build the prompt; never stored, never logged.

### `GET /api/stories?language=en` (new)
- Returns the shared gallery list: `[{ id, title, cover_url, age_tag, created_at }]`,
  newest first, from promoted columns only (no JSONB parse). `language` filter optional.

### `GET /api/stories/:id` (new)
- Returns one full story (the JSONB blob) with all per-page image URLs, for the viewer.

Not built yet (post-MVP): `DELETE`, admin upload, age filtering endpoint.

### New dependencies (approved)
- `@neondatabase/serverless` — serverless Postgres driver for Vercel functions.
- `@vercel/blob` — image upload/hosting.
Both are the Vercel-native minimum for this design.

## Image Generation Flow

### Config flag: `GENERATE_PAGE_IMAGES` (server env, `true` | `false`)
- `false` (cheap): cover only — ~$0.20/story, ~20s. Today's behavior.
- `true` (rich): cover + 5 page images — ~$1/story, ~25–35s with parallelism.

### Prompt builder change
The text model already returns a cover `scene`. Extend it to also return a short
`image_prompt` per page (a one-line visual description of that page's action):
```
pages: [ { text, image_prompt }, ... ]
```

### Parallel generation (in `+server.ts`)
1. Generate story text (1 call → title, 5 pages w/ text + image_prompt, moral, cover scene).
2. Build image prompts: cover scene + 5 page image_prompts, **each prefixed with the
   character's LOCKED `prompt_descriptor`** for cross-page visual consistency.
3. `Promise.all` all 6 image generations (fire at once, not sequential).
4. `Promise.all` all 6 Blob uploads.
5. Assemble `GeneratedStory` with URLs → INSERT → return.

### Known caveats
- **Character consistency is best-effort.** gpt-image-1 + locked `prompt_descriptor` keeps
  the hero recognizable across pages but not pixel-identical. Acceptable for MVP.
- **Partial image failure → no image for that page.** If a page's image fails, that page's
  `image_url` is `""` and the viewer renders **text-only** for it (NO avatar fallback — an
  out-of-context avatar is worse than no image). If the cover fails, the grid shows a soft
  placeholder tile. The story is always complete.

## Frontend Changes

### `generatedStories` store — becomes a thin API client
- `loadGallery(language)` → `GET /api/stories`
- `getStory(id)` → `GET /api/stories/:id`
- `addStory()` no longer writes localStorage (backend owns it).
- Small in-memory session cache so grid navigation doesn't refetch.
- **localStorage now holds only:** daily generation count (rate-limit) + language pref.
  No story data.
- **Removed:** the localStorage quota-eviction logic (no longer needed).

### Stories grid (`stories/+page.svelte`)
- Fetches shared gallery from backend. Still merges curated (bundled) + generated
  (backend), generated with the ✨ badge.
- Shows a brief loading state (now a network call) and a friendly "we need wifi to load
  stories" screen when offline.

### Story viewer (`stories/[id]/+page.svelte`)
- Fetches full story by id. Renders **each page as image-above-text** (image omitted if
  that page has none). Keeps the existing "can't find that story" fallback.

### Generating screen
- Mostly unchanged. Still POSTs then navigates to the new story. Slightly longer wait (6
  images); the existing character pulse animation covers it.

## Rate Limiting & Cost Guard

Two layers (shared gallery + no identity + ~$1/story makes this important):
1. **Client-side (keep):** per-device daily count in localStorage → instant "let's make
   more tomorrow" UX. No cost protection, just UX.
2. **Server-side global cap (new):** a single global daily counter in Postgres — max
   `DAILY_GENERATION_CAP` generated stories/day across everyone (default ~20). Exceeded →
   endpoint returns friendly `rate_limit`. Hard wallet protection while there is no
   identity. One small query; no extra service. Env-tunable without code changes.

## Error Handling

| Failure | Behavior |
|---|---|
| Invalid character/theme/language | `invalid_input` (unchanged) |
| Global daily cap reached | `rate_limit` + kid-friendly message |
| OpenAI text fails | `openai_failed` + "try after wifi" screen |
| A page image fails | That page renders text-only (`image_url` = "") |
| Cover image fails | Grid shows a soft placeholder tile |
| DB insert fails | `server_error`; story not shown (no partial gallery entry) |
| Offline gallery load | Friendly "we need wifi to load stories" screen |

## Scope Changes to `CLAUDE.md` (update as part of the work)

| Rule today | New reality |
|---|---|
| "Never add a database" | Postgres (Neon) stores generated stories |
| "The serverless function is the entire backend" | 3 endpoints + DB + Blob |
| "Cache every generated story to localStorage" | Backend is source of truth; online-only |
| "Per-page images out of scope (cover only)" | Per-page images in scope, behind a flag |
| "No Supabase/Firebase/other backend services" | Adds Neon + Vercel Blob (Vercel-native) |
